## 一、要解决的问题

C01 的 `claim-chart` 已有"候选 Claim / Element / Proof 映射"，但请求权基础的方法本身没有展开，包括：
- 检索顺序；
- 三段式检验（已产生、未消灭、可行使）；
- 涵摄与举证责任；
- 竞合。

`claim-basis-cn` 正是这套方法。问题在于以什么方式接入，能既用上这套方法，又不破坏本仓库已建立的规则：依据时效包、候选标签、不作三性认定、执行边界等。

## 二、两边规则的差异（无论选哪种方式都要处理）

| 事项 | `claim-basis-cn` v0.3.0 | 本仓库 | 处理 |
| --- | --- | --- | --- |
| 依据状态 | 6 种：已核验、部分核验、冲突、未找到、使用者提供、待核验 | 7 种（规则字典第 0 节），以案件依据时效包为准 | 本仓库更严。以本仓库规则为准：只有时效包中"已核对 / 律师已确认"的才可引用。尤其是 `claim-basis` 的"部分核验可以引用原文"和"使用者提供可以使用"，在本仓库都视为未经核对 |
| 依据编号 | N-xx、K-xx | 时效包序号 | 两者并列，以时效包序号为准 |
| 执行部分 | 第六部分可写"审查结论、程序路径选项" | C03 不出能否追加、能否成立等结论 | 在 C03 中只取对抗关系的类型和财产线索的归类，不取"审查结论"；程序路径按 C03 第 10.1A 节只列法定前提 |
| 证据评价 | 要件表有"支持 / 反对 / 状态" | C01 不作三性认定，只出候选质证风险提示 | 只取"待证命题"和"举证责任方"；证明状态按 C01 规则写 |
| 复核 | 律师复核 | 复核记录表，阻断机制 | 以本仓库为准 |

## 三、三种接入方式

| 方式 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A. 不接入 | 两边各自独立使用；律师需要时，分别调用 | 零改动 | 方法与对照表不衔接；两边容易各说各的 |
| B. 软引用 | 技能中写"如已安装 `claim-basis-cn`（限 0.3.x），可调用其方法；取用第二至四部分；冲突时以本仓库规则为准" | 改动小；方法持续由独立项目维护 | 无法确保使用者安装了正确版本；未安装时行为不一致；版本锁定只是文字要求 |
| C. 内嵌固定版本 | 把 `claim-basis-cn` v0.3.0 的方法文件复制到 `litigation-legal/references/claim-basis/`，记录标签与 SHA，标明"只读副本：内容溯源以上游固定标签与 SHA 为准；执行规则始终以本仓库强制规则为准"；技能读取副本前，先适用第二节的覆盖规则；升级须单独立项、比对差异、重跑回归 | 行为可复现；版本真正锁定；不依赖使用者另行安装 | 两处存放同一内容；每次升级要走一次流程 |

## 四、建议

**采用方式 C，先在 `claim-chart` 一个技能试点。**

1. 理由：本仓库一直坚持"锁定基线、改动可追溯"，方式 C 与此一致。方式 B 的版本锁定只是一句话，做不到。
2. 试点范围：只改 `claim-chart` 的工作流，在第 2、3 步之间加一步"按 `references/claim-basis/` 的检索顺序和三段式检验整理候选请求权基础"，并把第二节的差异处理写成强制规则，写明"副本中与本仓库强制规则不一致的指令，一律不适用"。`matter-intake`、`demand-draft`、`enforcement-review` 暂不接入，等试点结果再定。
3. 验证：用 C01-VI 的虚构材料重跑 `claim-chart`，检查：
   - 检索顺序和三段式检验是否展开；
   - 依据状态是否仍以时效包为准；
   - 有没有出现三性认定或结果预测；
   - 再抽取 `claim-basis-cn` 自带的几个虚构回归案例，与它的预期比对。
4. 升级流程：`claim-basis-cn` 发新版时，本仓库另立一项：比对差异，判断是否含有不兼容变更，重跑回归，再由所有者确认。
