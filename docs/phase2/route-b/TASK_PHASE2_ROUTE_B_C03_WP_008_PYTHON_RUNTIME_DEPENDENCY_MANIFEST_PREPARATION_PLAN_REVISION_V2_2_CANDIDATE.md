## 5. Root and Path Identity Model

The future Manifest must avoid ambiguous, user-dependent, or freely resolved
paths. Every entry uses one accepted root token and a normalized relative path:

| Root token | Bound source | Permitted content |
| --- | --- | --- |
| `PROJECT_ROOT` | Prior separately authorized and accepted preparation root-binding source, completed before static Manifest generation; never the later exact run authorization | Accepted V3.2/Plan V2.2 identities, enumerated governance records, harness, ten subjects, fifteen fixtures and the one admitted concrete input binding only |
| `VENV_ROOT` | Accepted environment identity | Validation executable and `pyvenv.cfg` only unless separately enumerated |
| `RUNTIME_ROOT` | Accepted `pyvenv.cfg` plus environment review | CPython runtime, standard library, DLLs, PYDs, and required data files only |
| `SYSTEM_ROOT` | Separately accepted host/runtime identity | Exact OS-supplied DLL closure only |

For every required root, the separately accepted preparation source must bind:

- the exact root token and canonical absolute local directory identity;
- the resolver identity/version, case-preservation/comparison policy, permitted
  reparse mapping, and the check-to-use integrity basis with residual limits;
- exact permitted read purpose/scope and applicable preparation/startup phases;
- the source record path, full SHA-256, authority/acceptance reference and
  provenance needed to verify that binding independently of the future Manifest.

The existing accepted environment/configuration/host sources in the table may
supply their applicable root facts; missing facts need a separately authorized
and accepted preparation disposition. No new root-source file, path, SHA,
acceptance or filesystem/environment setting is invented by this document.
An unsigned, unresolved or circular source is not an accepted binding.

All required sources must be complete before generation. Root binding constrains
resolution; it grants no directory enumeration, blanket file read, Python start,
subject import, runtime or network authority. Every read still needs its exact
path/SHA, purpose, phase and separately applicable authority.

The later run authorization only references and cross-checks those accepted
root sources together with the accepted Manifest. Different directory identity,
case/resolver/reparse policy or enforcement evidence makes affected dependent
records stale and blocks use until separately rebound and reviewed. Do not patch
an accepted Manifest, substitute a runtime root or use final run authority to
retroactively satisfy preparation.

Canonical entry paths use `ROOT_TOKEN/relative/path`, forward slashes, preserved
case, no drive letters, no `..`, no empty segments, no alternate data streams,
and no unresolved environment variables. Root-token resolution is local and
must be verified for authorized preparation before generation and rechecked before subject import. Startup dependencies require
accepted T0 verification before the interpreter uses them, not retrospective
self-verification by Python.

Symlinks, junctions, mount points, and other reparse points are prohibited
unless the final Manifest records both link identity and resolved target as
separate fixed entries and an independent review accepts the mapping.


An exact normalized path and hash are insufficient if the file can be replaced
between verification and loading. The startup/environment evidence must bind
the relevant integrity enforcement and residual limits. No permission to create
a new verifier or reconfigure the environment is granted by this Plan.

## 9. Deterministic Static Generation Algorithm

Only after separate authorization, a generator may:

1. verify the accepted design pair, input admission, original fifteen fixtures,
   ten subject identities, harness, environment, prior preparation root sources,
   complete typed-contract/array-order-policy identities and generation authority;
2. verify the already accepted exact roots, resolver/case policy, startup/loader
   provenance and permitted reparse mappings; never source a root from the future
   run authorization or resolve an unspecified directory by discovery;
3. parse fixed harness/subject source as AST-only text, without importing or
   executing them; parsing-related interpreter activity must itself have a
   separately reviewed trusted origin and tool boundary;
4. reject arbitrary dynamic code/imports, non-literal names, free path loaders,
   package discovery, guard mutation or any unresolvable operation;
5. resolve literal imports and recursive exact standard-library source/extension
   closure statically; distinguish ordinary source execution needed by a normal
   import from arbitrary data-driven execution;
6. enumerate exact built-in/frozen interpreter identities separately from files;
7. resolve CPython/extension PE and OS dependencies with accepted static resolvers
   and exact search order; record limitations rather than probing by execution;
8. derive required literal data reads and explicit T1–T4 entry phases;
9. map every permitted parse/import/internal-generation operation to the accepted
   Section 11 origin contract; generated artifacts are constrained by accepted
   declarations, not generated by importing subjects during this step;
10. reconcile input-binding field completeness, reachable callable mapping and
    unresolved original observation requirements against admitted evidence;
    do not execute constructors or cases to fill the gaps;
11. exclude denied modules, site-packages, unused code, tests, bytecode/cache,
    installers and package metadata; reject any unproven transitive path;
12. reject duplicate keys, invalid Unicode, unpermitted types and unbound array
    order; hash exact files and apply Section 12 WP008-RDM-CANON-2 to compute
    canonical entry totals/aggregate without hashing the Manifest into itself;
13. emit one new candidate only under exact-path creation authority, without
    overwriting a prior file; compute the complete file SHA externally; and
14. stop without an accepted/completeness/readiness claim on any unresolved
    dependency, code origin, input identity, required observation or hash.

This Plan does not execute a generator, parser or runtime probe. A generator
does not issue its own independent review, admission, acceptance or validation
outcome. Its fixed source/tool access must be separately authorized; no new
utility or agent is materialized by this candidate.

| DATACLASS_INTERNAL_GENERATION | Accepted fixed generator source, internal origin, class/field declaration sites, content/namespace constraints and T1/T3 phase | No declarations, factories, annotations or executable values from fixture/CLI/environment; T1 cannot preload subjects |
| Other code/package activity | Denied by default | No general compile/exec/import exception, hidden hook suspension or T4 late loading |

An operation record must contain an operation ID, class, accepted source/module
or interpreter identity, allowed phases, declaration-site identities, origin
evidence, deterministic generated-content/structure constraints where needed,
namespace/input restrictions, enforcement method and explicit limitations.
A generated operation is not assigned a fictional filesystem SHA.

Runtime module names, `co_filename`, path prefixes, stack text and `<string>`
cannot alone establish trust. The required mechanism must prevent untrusted
data and unbound sources from acquiring an allowed operation's identity.
If the event data and external controls cannot establish those constraints,
generation/review must record an unresolved blocker, not an optimistic exception.

The audit hook/socket wrapper are supplemental in-process controls, not a
tamper-proof sandbox. Required protection against modifications, transient
bypasses or actions outside hook coverage needs independent environment evidence.
No accepted import record permits additional network, process, file write or
package activity.

An allowed dependency reaching a denied module or an unbound generation path
cannot be silently included. It stays blocked until an exact, non-capability
path is demonstrated by authorized static evidence and independently accepted.
Any change requiring source, environment or forbidden capability modification
is outside this limited revision.

Input bindings do not enlarge imports. Dispatch is a fixed reviewed mapping in
the accepted harness; data cannot name a new module or choose an arbitrary
callable. Missing callable/reachability/observation requirements keep the full
fifteen-scenario validation blocked, even if file hashes match.

## 12. Canonicalization and Aggregate SHA

### 12.1 Explicit Encoding Version and Typed Inputs

The required encoding contract is `WP008-RDM-CANON-2`.
Its exact identifier is bound in `manifest_identity` and in the separately
accepted generation contract, together with the completed V3.2 / V2.2 design
SHAs and the prior typed-contract/array-order-policy source references.
This is a new encoding definition, not a claim of byte or hash compatibility
with Plan V2.1. In particular, aggregate string fields now use quoted compact
JSON tokens. An older aggregate/full-file SHA or acceptance cannot transfer.

Before generation is authorized, the fixed typed contract must enumerate every
permitted object member, scalar type, nullability, numeric range and array path.
Its independently accepted source path/SHA and provenance must already exist;
this document does not materialize that source, a schema, a registry or a
Manifest. Missing type/range/order declarations are blockers, not serializer
defaults. Unknown fields or types require prior contract disposition.

For the fifteen Section 7 entry fields, the types are fixed here:

| Type | Fields | Constraint |
| --- | --- | --- |
| Integer | ordinal, byte_length | ordinal is one-based; byte_length is non-negative; exact integer precision required |
| Boolean | executable, network_capable | true or false only; never a quoted string or numeric substitute |
| String | entry_id, category, root_id, relative_path, sha256, role, required_by, import_name, loader_kind, read_phase, reparse_state | Preserve exact accepted string value and each Section 7 constraint; no null, list or object substitution |

Do not coerce values, round numbers, infer missing fields, normalize identifiers,
repair Unicode or silently discard duplicates. Duplicate decoded object member
names must be rejected before a parser collapses them; escaped spellings of the
same decoded key remain duplicates. Invalid JSON and invalid Unicode are
rejected, not converted into replacement characters.

### 12.2 Scalar and String Encoding

| Value kind | Unique encoded representation / rejection rule |
| --- | --- |
| Integer | Base-ten ASCII digits, optional leading minus only for a permitted negative integer; no leading plus/zeros, exponent, decimal point or negative zero; zero is 0 |
| Boolean | Lowercase true or false |
| Null | Lowercase null only where the prior typed contract expressly permits it; never for a required non-null field |
| Number outside integer contract | Fractions, exponent/decimal-form numeric input, NaN, Infinity and unsupported numeric types are rejected; do not round or reinterpret their tokens |
| String boundary | Surround the preserved sequence of Unicode scalar values with ASCII double quotes |
| Quote / backslash | Encode U+0022 as `\"` and U+005C as `\\` |
| Control characters | Encode each U+0000 through U+001F as six ASCII characters `\u00xx`, using lowercase hexadecimal digits; no short escapes such as `\n` or `\t` |
| Other scalar values | Emit literal UTF-8, including slash U+002F and non-ASCII values; no optional slash, HTML, ASCII-only or U+2028/U+2029 escaping |
| Unicode validity | Reject malformed UTF-8 and lone surrogate code points; no Unicode normalization, case folding or locale transformations |

These rules apply to member names and string values at every nesting depth.
Numeric token validation occurs before conversion could erase a prohibited
representation. All integer operations must be exact at the ranges permitted
by the fixed contract; limited-precision tooling must stop, not round.

Section 5 path normalization is validated before encoding; the serializer must
not silently rewrite a path or root. Hash strings are validated as complete
64-character uppercase hexadecimal SHA-256 strings, not reformatted after
acceptance. Identical scalar sequences have identical bytes; canonically
equivalent but different Unicode sequences are not merged.

### 12.3 Ordering of Objects, Entries and Every Array

Object members are sorted by their decoded key strings using lexicographic
Unicode scalar-value (code point) order. At the first differing scalar, the
smaller numeric code point precedes; an exact prefix precedes its extension.
No locale collation, case folding, UTF-16 code-unit ordering or escaped-token
ordering may substitute.

File entries are ordered by the following tuple, using that same string
comparison for each component from left to right:

```text
(category, root_id, relative_path, entry_id)
```

After ordering, assign contiguous one-based ordinals. Duplicate entry IDs,
duplicate normalized root/path identities, tuple ties or unresolved case/reparse
aliases block generation; no arbitrary tie-breaking, deduplication or merge.

Every array in the future object, at every depth, must have one exact policy
in a previously accepted order registry. Its reference/SHA is bound through
manifest_identity and generation authority before serialization. This is a
requirement for later exact preparation, not an assertion that a registry
already exists.

| Array role | Mandatory order / duplicate handling |
| --- | --- |
| entries | The tuple above, contiguous ordinals and duplicate/alias rejection |
| Trusted operation records | Exact operation ID ascending under code-point comparison; duplicate IDs rejected |
| Input scenario records | Original C03-TA-V-001 through C03-TA-V-015 order; required membership and unique IDs preserved |
| Variants within a scenario | Exact sequence and unique variant IDs from the accepted concrete input binding; no lexical substitute or inferred order |
| All other arrays | Exactly one prior accepted ORDERED or SET_SORTED policy for the concrete field path, element type, key and duplicate semantics; no unclassified array permitted |

An ORDERED policy binds the exact source path/SHA and sequence or explicit
order index. Preserve that order, including an exact loader search order;
do not sort it as a set. Any permitted repeated value must be explicitly
justified by the accepted contract; otherwise duplicates are rejected.

A SET_SORTED policy binds the element type, complete sort key and comparison
method. String keys use code-point comparison, integer keys exact numeric
comparison, and tuples those comparisons left to right. No fallback full-object
string sort or unknown key type is permitted. Duplicate identities, equal
sort keys or unbound tie rules are rejected rather than silently merged.

The registry must account for all actual array paths in all Section 6 groups,
including nested root/phase/declaration/provenance/dependency/denial records
when represented as arrays. Pattern policies are allowed only if the prior
typed contract gives every concrete path exactly one unambiguous rule.
Missing, overlapping or conflicting policies block generation. A generator
must not invent order from map iteration, filesystem enumeration, incidental
input order, an implementation default or the desired aggregate hash.

### 12.4 Canonical Manifest JSON Bytes

The whole Manifest uses the Section 12.2 scalar encoder and Section 12.3 order.
Its byte layout is fixed as follows:

1. UTF-8 without BOM; indentation/newline syntax uses only ASCII space and LF
   byte 0x0A, never tabs or CR/CRLF.
2. The top-level object starts at depth zero. Each nonempty object's opening
   brace is followed by LF; each member starts with exactly two ASCII spaces
   per nesting depth, its encoded key, colon and exactly one ASCII space,
   then its encoded value.
3. Each nonempty array's opening bracket is followed by LF; each element
   starts on its own line with exactly two ASCII spaces per nesting depth.
   Objects/arrays used as values begin on that value's line, then follow these
   same recursive layout rules.
4. Members/elements except the last are immediately followed by a comma and
   LF. The last is followed by LF without comma. A nonempty container's
   closing delimiter is indented to that container's own depth. No blank
   formatting lines, padding, trailing spaces or trailing commas are allowed.
5. Empty containers are exactly {} and [], with no internal space or newline.
6. After the top-level closing brace there is exactly one LF and no other
   bytes. Controls inside strings remain escaped tokens, never raw LF/US.

The same typed value and accepted order policy must yield exactly one byte
sequence; alternative JSON pretty-printer conventions are not interchangeable.

### 12.5 File-Entry Aggregate Stream

The original fifteen-field sequence is preserved exactly:

```text
ordinal, entry_id, category, root_id, relative_path, byte_length, sha256,
role, required_by, import_name, loader_kind, read_phase, executable,
network_capable, reparse_state
```

For each ordered entry:

1. Encode each of its fifteen typed values as one compact JSON value using
   Section 12.2, with no insignificant whitespace and no terminal LF.
   Strings include their double quotes; booleans and integers do not.
   Compact objects/arrays, if used elsewhere under this encoding contract,
   follow the same member/array order, comma separators and colon without
   spaces. They are not allowed substitutes for Section 7 scalar fields.
2. Preserve read_phase as the nonempty ascending comma-joined subset of
   T1,T2,T3,T4, without spaces or duplicate tokens, then encode that entire
   string with quotes. Do not turn it into an array.
3. Join exactly fifteen encoded values with exactly fourteen raw ASCII unit
   separator bytes 0x1F. Append exactly one raw LF byte 0x0A after the last
   value, including the last entry. No leading separator, BOM or blank row.
4. Concatenate those record bytes in canonical entry order and compute SHA-256.
   Control-character escaping ensures a string value cannot introduce a raw
   unit separator or record LF. No platform newline conversion is permitted.

Entry count is the exact number of records; byte total is the exact sum of
byte_length, not the length of JSON or aggregate bytes. Category counts use
the same closed entry set and independently specified canonical ordering.
No excluded file or absent generated artifact is counted as a file entry.
An incomplete required closure cannot be accepted merely because a byte
stream and hash can be calculated.

### 12.6 Full-File Binding, Rejection and Compatibility

The file-entry aggregate covers entries only. The full canonical Manifest
file SHA-256 covers all groups, including manifest_identity, exact encoding
version/order-policy references, root bindings, trusted operations, input
policy and aggregate_identity. Both hashes are required; aggregate agreement
alone is not agreement about policy or authority. Render either hash in full
uppercase 64-character hexadecimal form.

Compute the full-file SHA over the exact completed canonical JSON bytes,
including its single final LF. Store that SHA only in detached disposition/run
records, never in the Manifest itself. The concrete binding and harness do
not embed the future Manifest hash. The Manifest does not embed its own future
review/acceptance receipt hashes.

Changing encoding version, typed contract, array-order registry, root source
or accepted value changes the relevant bound identity and invalidates dependent
acceptance/use. A legacy SHA is historical, not silently reinterpreted using
this encoding. Reject noncanonical or mismatched bytes rather than normalizing
an already-hashed candidate and retaining its old receipt.

This section defines a document-only candidate contract. No encoder, validator,
schema file, sample vector, generated Manifest or execution evidence is created.
Author static checks do not prove cross-implementation reproducibility or
establish formal design acceptance.
