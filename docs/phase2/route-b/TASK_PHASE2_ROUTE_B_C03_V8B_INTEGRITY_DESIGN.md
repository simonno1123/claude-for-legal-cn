## 一、要解决的问题

V8-A 只检查记录内部是否一致，下面三件事它挡不住：

1. **记录是谁作出的。** R、AUTH、Q3 都由记录人转录，没有任何东西能证明这些答复出自复核人本人。"AI 不作复核人"这条底线，目前在技术上没有保障。
2. **时间是否真实。** 记录里的时间都是记录人写的，无法防止倒填。
3. **授权是否被重复使用。** G 只在单个文件夹内计数。

## 二、信任边界（R1 的根本缺陷与 R2 的前提）

记录人（Claude）能写仓库、能写所有者连接的文件夹，并以所有者的 GitHub 账号操作。所以公钥清单、校验程序、使用登记、时间锚点，只要有一项放在这些地方，记录人就能替换或回退，签名也就防不了代签。

R2 的前提是把信任根移出记录人可达的范围：

1. **信任文件夹。** 所有者在自己电脑上建一个文件夹，**不连接**给任何 Claude 会话，下文称"信任文件夹"。记录人既看不到，也写不了。里面放：
   - `allowed_signers`：复核人公钥，角色代号 `REVIEWER-01`，用途命名空间 `c03-gate`；
   - 校验程序的副本（`v8b/`），由所有者从已合并的主分支复制，并记下其 SHA-256；
   - 全局使用登记与锁文件（第六节）；
   - 时间锚用的盐（第五节）。
2. **私钥。** 放在所有者用户目录的 `.ssh` 下，设口令。记录人不得、也不能输入口令。
3. **由所有者本人运行。** 签名、全链校验和最后的"使用"一步，都在所有者自己的终端里运行：Windows 自带的 OpenSSH `ssh-keygen` 和本机 Python，运行的是信任文件夹中的程序副本。记录人只负责给出命令文本。**记录人不再运行 `record-use`。**
4. **程序副本的可信性。**
   - 安装或升级时，所有者用 Windows 自带的 `certutil -hashfile <文件> SHA256` 计算副本的哈希，与该版本合并 PR 中公布、并经 Codex 评审的 SHA 比对，一致才写入信任文件夹。
   - 之后每次运行，都用信任文件夹中的副本，不用连接文件夹或仓库中的版本。
   - 记录人改动仓库代码，不影响已安装的副本；升级必须由所有者重新比对、重新复制。
5. **不能消除的。** 一人集中：所有者本人仍可改动信任文件夹。V8-B 防的是记录人代签、倒填和重放，不防所有者本人。可验证的模型来源（V8 设计第九节第 3 项）也做不到，保留为局限。

## 三、B1：分阶段的封闭签名

R1 的问题是：签名覆盖的是"整个文件夹"，而后续阶段必然新增记录，正常流程也会校验失败。R2 改为每个阶段签一份**封闭清单**，只覆盖该阶段列明的记录。后一阶段的清单引用前一阶段签名的 SHA，形成签名链。

| 阶段 | 封闭清单覆盖的记录 | 签名前所有者本人运行的检查 |
| --- | --- | --- |
| S1 复核承诺 | M、I、T、全部 V、W、X（L2）、R，以及 R 所含停点答复引用的发现与解除事件 | V8-A `review` 阶段。L1 必须通过；L2 只要求除"P 缺失"以外全部通过（新增检查阶段 `review_commit`，见下文） |
| S2 冷却后重确认（仅 L2） | P，加上 S1 签名的 SHA | V8-A `review` 阶段全部通过（此时 P 已存在） |
| S3 授权 | Q1、申请正文、Q2、AUTH，加上前一阶段签名的 SHA | V8-A `authorization` 阶段 |
| S4 使用 | Q3、G 当前前缀的 SHA、前一阶段签名的 SHA、本次调用的挑战值和登记序号 | 第七节的执行时全链重验，**在同一次运行中**签名并执行 |

- **`review_commit` 阶段。** 只放宽"L2 缺 P"一条，其余规则不变。这一阶段在包装层实现：调用 V8-A `review`，剔除唯一的 `RECONFIRMATION_MISSING` 后，判断是否还有其他理由码。V8-A 核心不改。
- **G 的变化。** S4 签的是使用之前 G 的前缀。使用事件追加之后，校验时核对"G 的前 n 行与 S4 签名的前缀 SHA 一致，第 n+1 行是本次使用事件"。
- **签名命令。** `ssh-keygen -Y sign -n c03-gate -f <私钥> <清单文件>`。清单按 RFC 8785 规范化。
- **校验。** `ssh-keygen -Y verify`，只信任信任文件夹中的 `allowed_signers`；仓库或连接文件夹中的公钥清单一律不读。
- **新理由码。** `SIGNATURE_MISSING`、`SIGNATURE_INVALID`、`SIGNED_MANIFEST_MISMATCH`、`SIGNATURE_CHAIN_BROKEN`。

## 四、复核人的操作负担

每份候选，所有者本人在终端运行：

| 次数 | 内容 |
| --- | --- |
| L1：3 次 | S1、S3 各运行一次"检查＋签名"；S4 运行一次"重验＋签名＋使用"。每次输入一次口令 |
| L2：4 次 | 另加 S2 |

记录人每次给出完整命令。所有者需要先在终端里看到检查结果，再输入口令。

## 五、B2：可信时间锚（可选）

R1 的问题是：GitHub 评论可以编辑，创建时间不能证明正文的时间。R2 改用**推送记录**：

1. **锚点仓库。** 所有者新建一个私有仓库。每次签名之后，把一个只含加盐摘要的提交推送上去：摘要为 SHA-256(盐 ‖ 签名文件 SHA-256)，盐每案件随机生成，放在信任文件夹。
2. **时间来源。** 取 GitHub 仓库活动接口（`/repos/{owner}/{repo}/activity`）返回的推送时间。推送时间由服务器记录，不能编辑。提交自身的时间可以伪造，不使用。
3. **校验。** 所有者本人运行，规则如下：
   - 摘要所在提交必须出现在一次普通推送中；如果该分支有过强制推送或删除，一律拒绝；
   - 时间约束：S1 锚点 ≥ R 的 `formed_at`；L2 中 S2 锚点 − S1 锚点 ≥ 24 小时；S4 的执行时刻（第七节）< 有效截止。
4. **新理由码。** `TIME_ANCHOR_MISSING`、`TIME_ANCHOR_MISMATCH`、`TIME_ANCHOR_REWRITTEN`、`ANCHORED_ORDER_INVALID`。
5. **证明力与局限：**
   - 锚点证明"签名文件至迟在推送时已存在"，因为摘要依赖签名内容，不能事先生成。它不证明"至早"。
   - 记录人用所有者账号也能推送；但推送只能让时间更晚，不能更早，所以不构成倒填途径。删除锚点只会导致校验失败。
   - GitHub 活动记录的保留期限有限。所以锚点只在使用时点校验，此后的长期审计只能依赖本机保存的活动记录副本，这份副本不可验证。
   - 依赖 GitHub 的可用性和服务器时间。

## 六、B3：全局使用登记与恢复

1. **位置。** 登记放在信任文件夹，一行一条 JSON，只追加，从不截断。每行包括：序号、上一行的 SHA、授权 SHA、案件代号、事件类型、时刻。事件类型为"意图"、"已提交"、"已放弃"三种之一。
2. **锁。** 一把全局锁（信任文件夹中的锁文件，排他创建）。加锁顺序固定：先取全局锁，再取该复核文件夹的 G 锁；解锁顺序相反。读取使用次数之前就必须已持有全局锁。
3. **执行协议**（第七节"使用"命令的内部步骤）：
   1. 取全局锁，读登记。如果有"意图"行既没有"已提交"也没有"已放弃"，立即阻断（`REGISTRY_RECOVERY_REQUIRED`）。
   2. 已提交的使用次数达到 `max_uses` 的，拒绝（`AUTHORIZATION_REPLAYED`）。
   3. 追加"意图"行，取 G 锁。
   4. 复制候选，追加 G 使用事件。
   5. 追加"已提交"行，解锁。
   6. 第 4 步失败时：复制出的候选移入作废文件夹（只移动，不删除）；G 按现有方式回滚；登记追加"已放弃"行，**不截断**，所以不会误删其他使用的登记。
4. **中断恢复。** 进程中断后留下孤立的"意图"行。所有者本人运行恢复命令：逐项核对候选、G 和登记的实际状态，再追加"已提交"或"已放弃"。恢复完成之前，所有使用一律阻断。
5. **AUTH 增加 `nonce`**（16 字节随机数）。S3 签名覆盖 nonce；复制授权文件到别处，不能产生新的授权。
6. **防删尾回退。** 登记在信任文件夹内，记录人无法截断或回退。S4 签名覆盖本次登记序号，后续使用的签名再覆盖更大的序号：登记一旦被截回，已签名的序号就对不上，校验失败。

## 七、执行时全链重验（"使用"命令）

所有者本人运行一条命令，在同一次运行中依次完成：

1. 生成本次调用的挑战值（随机数）。
2. 取锁，读登记（第六节第 3 条第 1、2 步）。
3. 重新校验整条链：
   - S1 至 S3 的签名与封闭清单；
   - B2 锚点（启用时）；
   - 以**当前时刻**运行 V8-A `use` 阶段；
   - 当前撤回状态，读复核文件夹和案件目录中的撤回与叫停记录；
   - 停点索引中 Q3 之后有没有新增发现事件。有新增的，阻断（`NEW_STOP_AFTER_Q3`）。
4. 全部通过后，生成 S4 清单（含挑战值和登记序号），提示所有者输入口令签名。
5. 签名成功后，执行第六节第 3 条第 3 至 5 步。
6. 当前时刻已到或超过有效截止的，任何一步都不执行（`VALIDITY_EXPIRED`）。

旧的成功结果不能代替这次运行：校验、签名和使用发生在同一进程、同一把锁内。

## 八、测试

1. 每个新理由码各一组反例，使用测试专用的虚构密钥和虚构数据。
2. 正向路径：L1（S1、S3、S4）和 L2（S1、S2、S3、S4）各一条。锚点读取在测试中用替身代替。
3. 信任根：仓库中放一份伪造的 `allowed_signers`，校验必须不读它；签名公钥不在信任清单中的，拒绝。
4. 封闭清单：S1 签名后新增 AUTH、Q3、G 事件，S1 校验仍然通过；改动 S1 覆盖的任何一份记录，失败。
5. 并发：两个文件夹同时使用同一授权，只有一个成功；中断后留下孤立"意图"行时阻断；恢复后可以继续。
6. 删尾：登记截回之前的状态后再使用，失败。
7. 锚点：分支有强制推送记录的，拒绝；S2 − S1 不足 24 小时的，拒绝。
8. 接入现有 CI（使用替身，不访问网络）。

## 九、R1 评审意见的处理

| 编号 | 级别 | 意见 | R2 的处理 |
| --- | --- | --- | --- |
| 1 | P0 | `allowed_signers` 放在记录人可写的仓库，不是独立信任根 | 第二节：信任根移到所有者的非连接文件夹；校验程序以副本运行，按已评审的 SHA 安装；仓库中的公钥清单不读 |
| 2 | P1 | "整个文件夹"清单与后续阶段冲突；G 必然变化 | 第三节：分阶段封闭清单加签名链；S4 签 G 前缀 |
| 3 | P0 | 评论可以编辑，创建时间不能锚定正文 | 第五节：改为不可编辑的推送时间；强制推送或删除一律拒绝 |
| 4 | P1 | L2 没有 P 的签名和锚点；R 后 V8-A `review` 因缺 P 失败 | 第三节：新增 S2；S1 使用包装层的 `review_commit` 阶段，只放宽"缺 P"一条 |
| 5 | P0 | 旧的成功结果可被沿用；执行边界没有重验 | 第七节：挑战值、全链重验、当前撤回和停点状态，同一进程内签名并执行 |
| 6 | P0 | 全局登记没有跨文件夹锁；回滚可能截掉他人的登记 | 第六节：全局锁先于 G 锁；意图、已提交、已放弃三段登记，只追加不截断；中断恢复协议 |
| 7 | P0 | 删尾回退可绕过 | 第六节第 6 条：登记移到信任文件夹；签名覆盖单调递增的序号 |
