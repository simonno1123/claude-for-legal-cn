## 一、要解决的问题

V8-A 只检查记录内部是否一致。首例试用暴露了三类它挡不住的情况：

1. **记录是谁作出的。** 复核人的处置（R）、授权（AUTH）和使用前核对（Q3）都由记录人转录。记录里没有任何东西能证明这些答复出自复核人本人，而不是记录人自己写的。这正是"AI 不作复核人"这条底线目前唯一没有技术保障的地方。
2. **时间是不是真的。** `formed_at` 是转录时间。24 小时冷却期、有效截止，都只能比较记录自己写的时间，无法防止倒填。
3. **授权有没有被重复使用。** G 只在一个复核文件夹内计数。把同一份授权复制到另一个文件夹，再用一次，V8-A 发现不了。

## 二、设计取舍：先做能用、负担小的三项

V8 设计第九节列了五项，逐项判断如下：

| 第九节事项 | 本设计 | 理由 |
| --- | --- | --- |
| 2. 信任根与数字签名 | **做（B1）** | 解决第一节第 1 个问题，价值最大 |
| 1. 可信时间与调用新鲜度 | **做（B2）**，用第三方服务器时间作锚 | 设备上无法访问公共时间戳服务（RFC 3161），见第四节 |
| 4. 跨次防重放、一次性使用登记 | **做（B3）** | 实现简单 |
| 5. AR-B-010 执行边界的独立重验 | **并入 B1**：复核人本人在自己的终端运行校验，再签名 | 见第三节第 3 条 |
| 3. 可验证的模型来源 | **不做**，保留为局限 | 目前没有任何方式能验证对话中实际是哪个模型在作答 |

不变的局限：本项目只有一名执业律师，密钥、时间锚和登记都由同一人掌握。V8-B 防的是**记录人**代签、倒填和重放，不能消除一人集中。

## 三、B1：复核人签名

1. **密钥。** 复核人在自己的电脑上用 OpenSSH 生成一把 Ed25519 签名密钥，设口令。
   - 私钥放在用户目录的 `.ssh` 下。这个位置记录人访问不到：连接文件夹中的 `.ssh` 等凭据位置受保护，记录人也不得输入口令。
   - 公钥写入仓库的 `validation/route_b_c03/v8b/allowed_signers`。公钥本身不含个人信息，注释字段只写角色代号 `REVIEWER-01`。
2. **签什么。** 签名对象是一个"签名清单"：本次复核文件夹中每份记录的文件名和 SHA-256，再加上 V8-A 校验结果，按 RFC 8785 规范化，与 V8-A 的规范化方式一致。签名用 `ssh-keygen -Y sign -n c03-gate`，命名空间固定，防止别的用途的签名被挪用。
3. **何时签。** 三个时点各签一次：
   - **复核签名：** R 形成之后，复核人本人运行 `gate_cli.py verify <文件夹> --stage review`，看到结果后签名；
   - **授权签名：** AUTH 形成之后（`--stage authorization`）；
   - **使用签名：** Q3 形成之后、record-use 之前（`--stage use`）。

   "本人运行校验后再签"就是第九节第 5 项要的独立重验：记录人的运行结果不作数，以复核人终端上的结果为准。
4. **校验。** 校验时用 `ssh-keygen -Y verify` 核对签名与 `allowed_signers` 中的公钥。缺签名、签名不符、清单与文件不符、签名之后又改过记录，都会阻断。
   - 新理由码：`SIGNATURE_MISSING`、`SIGNATURE_INVALID`、`SIGNED_MANIFEST_MISMATCH`。
   - 签名校验放在包装层，V8-A 的核心函数保持纯函数。
5. **复核人的负担。** 每份候选多三条命令。记录人给出完整命令，复核人复制运行、输入口令。复核人不想用命令行时，这一项可以不启动（见第七节）。

## 四、B2：可信时间锚

**现状：** 在所有者设备上测试，公共时间戳服务（freetsa.org、DigiCert）都连不上，一个超时，一个被代理拒绝。

**方案：** 用 GitHub 服务器时间作第三方时间锚。

1. 每次 B1 签名之后，记录人把一个**加盐摘要**写到一个**私有**仓库，作为一条 issue 评论。加盐摘要的算法是 SHA-256(盐 ‖ 签名清单 SHA-256)，盐是每案件随机生成、只存在本机的 32 字节值。
   - GitHub 记录的评论创建时间由服务器生成，记录人无法改写，可以作为"这个摘要至迟在此时已存在"的证据。
   - 摘要加了盐，不加盐的摘要也不进入公开仓库。这与"不在公开仓库写真实文书哈希"的规则一致。
2. **校验。** 校验时读回锚点评论，比对摘要，并用锚点时间核对：
   - 复核锚点时间 ≥ R 的 `formed_at`；
   - L2 中 P 锚点 − R 锚点 ≥ 24 小时；
   - 使用锚点 < 有效截止。

   新理由码：`TIME_ANCHOR_MISSING`、`TIME_ANCHOR_MISMATCH`、`ANCHORED_ORDER_INVALID`。
3. **局限：**
   - 锚点只证明"至迟"，不证明"至早"，仍可能拖延后再锚；
   - 依赖 GitHub 的可用性和服务器时间；
   - 私有仓库由所有者控制，所有者可以删评论，但删除会使校验失败，而不是通过。
4. **需要所有者决定：** 是否新建一个私有仓库专门存锚点。备选方案是不做 B2，只做 B1 和 B3。

## 五、B3：跨次防重放与一次性使用登记

1. 在所有者本机私有目录的根部（不在某个案件目录内）建立**全局使用登记**，一行一条 JSON，只追加。每行记：授权记录 SHA、案件代号、使用时刻、本行的前一行 SHA。
2. `record-use` 在现有的加锁步骤内多做两件事：
   - 先查全局登记：同一授权 SHA 的使用次数已达到 `max_uses` 的，拒绝使用，理由码 `AUTHORIZATION_REPLAYED`；
   - 通过后，先追加全局登记，再追加 G。任何一步失败，两处一并回滚，沿用现有的 G 回滚做法。
3. 每份 AUTH 新增随机值 `nonce`（16 字节），由工具生成，写入签名清单。复制授权文件到别处，不能产生新的授权。
4. **局限：** 全局登记本身没有签名，删行可以绕过。启用 B1 时，每次使用签名都覆盖全局登记的当前末行 SHA；删行后，之后的签名校验即失败。

## 六、测试

1. 各新理由码各一组反例，使用虚构密钥和虚构数据，测试密钥只用于测试。
2. 正向路径：L1、L2 各一条，含三次签名和锚点（锚点读取在测试中用替身代替）。
3. 重放：同一授权在两个文件夹各用一次，第二次被拒；全局登记追加失败时，G 不变。
4. 签名后改动任一记录，校验失败。
5. 接入现有 CI。
