## 0. 形成边界

- 没有运行解释器，没有导入或执行任何被复制的文件，也没有执行任何仓库模块。
- 没有读取工具缓存，没有读取 `ENVIRONMENT_MANIFEST.md`。
- 没有调用 `identity_gate`，没有执行 Fixture 或场景运行器。

## 1. 这台机器不是记录中的验证机

本机与仓库记录的验证机是不同的 Windows 主机：用户配置文件不同，"文档"里没有项目工作副本，用户目录下也没有工具运行时缓存。所以本候选是新主机上的新观察，不能作为此前记录环境的证据。

## 3. PE 与 OS

- 44 个 PE 文件全部是 x86-64，都带有 Authenticode 签名块。签名本身没有验证。
- 导入表用两个读取器解析：一个最小静态读取器（普通导入和延迟导入），以及 `llvm-objdump` 18.1.3（只读普通导入）。两者在全部 44 个文件上的普通导入一致。`llvm-objdump` 不列延迟导入名，延迟导入只来自前一个读取器。唯一的延迟导入是 `_wmi.pyd` → `ole32.dll`。
- 运行时内部之外的依赖是 23 个具名系统 DLL 和 14 个 API-set 名称，名单和各自的使用者写在 `OsDependencyNames`。
- 系统 DLL 的字节和 SHA 没有取得。系统 DLL 文件夹的读取已获批准，但文件桥拒绝了每一个系统 DLL，原因是它们都是硬链接（指向组件存储）。API-set 名称也没有解析到具体的主机 DLL。

## 4. 导入闭包

起点是批次 Harness 的直接导入（REV18 盘点）加上受测文件的直接导入（准备计划第 4 节）。

| 闭包 | 规则 | 结果 |
| --- | --- | --- |
| 导入时闭包 | 模块体和类体，包括顶层 if / try 分支；不含函数体 | 闭合。68 个 Lib 文件，全部散列 |
| 全边上界 | 所有 import 语句，包括函数体 | 未闭合。已解析 102 个模块，仍有 16 个文件未读 |

导入时闭包里有 41 个名称不是 Lib 文件：3 个对应 `DLLs` 里的 PYD，3 个是 Windows 上不存在、由平台分支挡住的模块，其余 35 个应是内置或冻结模块，但没有办法静态核实。按名字在运行时加载的编码模块也无法静态解析。

## 5. 所见

- `OD04-LFR-F01`：本机不是记录中的验证机。
- `OD04-LFR-F02`：候选是固定的、按用户安装的 3.12.10，不会像工具缓存那样被自动替换。这正是 REV18 指出的前提条件。
- `OD04-LFR-F03`：运行时的 PE 身份和导入表已取得；对外依赖只剩系统 DLL 和 API-set。
- `OD04-LFR-F04`：系统 DLL 的字节因硬链接被文件桥拒绝，没有记录。
- `OD04-LFR-F05`：导入时闭包已闭合并散列。
- `OD04-LFR-F06`：全边上界未闭合。
- `OD04-LFR-F07`：CPython 3.11 起，部分启动模块（如 `os`、`stat`、`ntpath`、`codecs`、`io`、`abc`）从 `python312.dll` 里的冻结副本加载，因此这些 Lib 文件的 SHA 不是实际运行的代码。另外，看到的 Lib `__pycache__` 文件写于 2026-10-30T21:03Z，说明 Lib 目录对当前用户可写，里面有加载器可能优先使用的字节码。这两点都限制检查到使用的防替换。冻结模块清单是 CPython 的一般行为，没有在本机核实。
- `OD04-LFR-F08`：只读文件访问且不运行的条件下拿不到的有：T0 启动前核验、两侧调用身份、检查到使用的保护、系统 DLL 字节。Harness 和受测源码也不在本机上。
